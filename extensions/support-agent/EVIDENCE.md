# 缺证判断、针对性追问与扩充业务资料（V4.1）

这是已有知识检索工具的增量：同一套 BM25 / 向量融合 / 重排结果，在进入模型前增加信息需求检查。它不训练模型，不把相关性分数当正确率，不修改工单角色与人工确认规则。默认仍是关键词检索。

## 现在如何演示

在 https://localhost:8443/console/knowledge 选择关键词检索，试用：

- `这里不行了，帮我看看。`：补问具体业务对象和现象。
- `批量登记不成功。`：对象已经提供，补问发生步骤与错误现象。
- `邀请链接有效期多久，年度报价多少钱？`：保留邀请链接有效期的依据，同时指出没有报价资料。
- `误删文件永久删除后，客服保证能恢复吗？`：按原文限制解释不能保证，不把否定依据当作应全部拒答。

LibreChat 正常 Agent 的提示词也已更新：补充上下文后重新形成完整检索问题；逐项核对原文；已知部分可答，缺项单独说明；不得要求密码、验证码、完整密钥或重置链接。固定 alice 的工具身份仍然不随浏览器账号切换。

新增业务资料在 `data/documents/support-supplement.md`，正文逐字对应 `supplement.json`，摘要与位置见 `supplement-manifest.json`。新增 16 篇包括离职交接、外部审阅、团队调整、编辑冲突、审批、采购、台账与归档等；没有专门给旧失败问题补数字。**全部为项目自编模拟业务规范，不是实际企业制度，也不是对本机功能的描述。**

补充手册已通过管理员的真实上传入口导入 `KD-43EC19C86B399D47C721A267` v1，17 个分块；同文件重试复用版本，员工可读取原文。原 16 篇正文、原手册 7 块和历史版本不变。独立业务条目合计 32，正式扩充语料评测只使用原手册＋补充手册共 24 块，不混入原种子的重复副本或功能说明文档。

## 实现边界

`app/evidence.py` 按业务问题的分句识别精确需求，例如价格、税率、数量上限、事件时长、保留期、地域、算法及保证；明确区分同一主题下不同对象的属性。数值必须与所问对象和事件处于可关联的原文语句，不能从标题借主体、从重置链接借锁定时长、从试验批次借产品容量，也不能用标准版规则证明企业版规则。

对于同一条请求中紧邻的明确事件，可以承接短时长问句；不假装服务端保存了任意聊天上下文。草稿/提案的明确过期时间可以说明该临时对象的可用期限，不能推广为普通日志留存或保留权限时长。

`app/retrieval.py` 返回原有三种 `evidence_status`，并新增 `evidence_assessment`：

| 字段 | 含义 |
| --- | --- |
| `coverage` | `none`/`partial`/`full`，仅指启发式识别的信息项；不是答案正确率 |
| `supported_claims` | 需求标签与原文 quote、doc_id、revision、chunk_id、绝对 offset |
| `missing_information` / `missing_requirements` | 缺少哪一类事实与规则代码 |
| `missing_fields` | 需补充的 object / symptom / operation |
| `clarification_questions` | 最少且具体的追问；不索取秘密 |
| `assessment_scope` | 明确这是启发式检查，或一般候选仍需模型核对 |

全部缺证返回 `insufficient` 且不提供可被当作答案的候选；部分可答仍返回 `candidates`，明确缺项；含糊请求返回 `clarify`。一般业务说明未必能被这些有限规则证明，因此 `full` 不能解读为整个回答已被语义验证。页面对这种情况显示“找到相关候选，尚未逐项验证”。真实来源、位置正确也不代表引用能证明所问事实。

V4.1 进一步区分业务规则咨询与故障求助；时间单位先于普通数量判断，明确询问试验或示例数量时可使用限定范围的数据。承诺与否定性依据也必须关联所问事件，不能把准备期限、后续链接寿命或另一业务的否定句当作处理承诺。

三种检索模式共用这层策略，`HybridRetriever` 允许可信代码注入冻结旧策略以做对照；该注入不向 HTTP 用户开放。组织隔离、返回前身份复核、不安全文档隔离、内部 raw 候选不外泄仍沿用原边界。现有 12 个工具不增减。

## 评测如何避免混淆

旧 V3.1 检查策略冻结在 `evaluation/frozen_v31`。新旧策略拿到的是同一次真实检索的同一份前 3 块，内容、顺序、分数固定；比较中只改变证据判断与追问。它衡量工具层规则行为，不衡量生成答案是否正确，也不把扩充资料的效果混成算法收益。

`evaluation/evidence_cases_v4.json` 在运行前冻结 48 个不同问题：开发 16、首次测试 32。测试组为可答 10、精确缺证 6、明确否定可答 4、部分可答 6、追问 6。标准包含原文与允许的安全处置集合；部分问题保守拒答可以符合安全标准，但另行报告已知证据丢失和过度拒答，不能称为完整解决。开发过程可调整实现，正式测试后不据结果改分或调参。

旧 hybrid 36 题仅作已见回归，保留原题标签和负向问题的标签边界，不修改上一轮结果。开发模型观测及各轮离线重判保留在独立目录，修策略与修评分器的原因分别记录。全量返回来源必须可验证；新增结构化字段不能让同一句追问获得比旧结构更宽松的标准。

VS Code 的两个新任务：

- `Support: Evidence policy development (16 cases)`
- `Support: Evidence policy regression (32 fixed cases)`

都调用 `evaluation/evidence_run.py`，在 `.local/evidence-evaluation/<时间>` 新目录输出原始数据、HTML、输入/代码/模型摘要。需要已完成 `Prepare CPU retrieval models`；两种模式按顺序在 CPU 执行，不调用付费生成模型。首次留出验证之后再次运行，只能称固定集回归。

另做少量真实 DeepSeek 只读验收：复制正常 Agent 的模型与新指令，创建私有 3 工具验收副本（身份、检索、原文证据），结构上不能写工单。正常 Agent 保留 12 工具。检验 7 个任务、8 次用户消息的真实工具轨迹、回答、来源和用量；回答需逐条辅助语义复核，不靠关键词自动宣布全部正确，不冒充人类验收。

V4 首次新 32 题的严格规则符合率为旧策略 18/32、新策略 21/32，两个正常问题被过度拒答。该结果原样保留；随后修正为 V4.1，原 32 题只作已见回归，并另设 16 道小型留出。不得用修后的已见回归覆盖首次结果，或合并不同题集分母。

完整实测结果见 [VALIDATION.md](VALIDATION.md) 与工作区的 `outputs/LibreChat-缺证追问与扩充复测.html`。原 100 条 Agent 95/100 基线和上轮混合检索数字保持不变。

## 当前实测边界

V4.1 另设的首次 16 条小型留出，旧策略 8/16 → 当前 12/16 严格规则符合（两种模式相同）；6 条正常可答与 2 条明确否定均保留正确原文。2 条精确缺证识别 1/2，4 条追问中仅 1 条满足全部针对性要求；2 条部分可答均以允许的保守拒答通过，但已知证据保留为 0/2，因此不能解读为部分回答已全面完成。追问之一虽然返回 clarify，却问了不必要的故障现象而没有补清操作意图，也应算不够针对。

剩余实质问题包括人数单位/主体与重试次数混用、未识别的新指代表述、以及“没记录提示”的信息缺失表达。首次结果不据这些失败再改分或重新择优运行；这些是下一轮需处理的边界。来源位置有效不代表语义支持，必须保留这个区别。

原 32 条在修复后仅作已见缓存回归，自动规则为 30/32；两条追问被词族评分器把“这个功能中完成什么操作”误读为再次询问对象，不能直接称两条错误答案。仍保留自动分数，辅助语义意见单列。新 16 条的 4 个失败为实质能力边界，不是同一类评分误报。

真实Agent首轮7任务/8消息完成后，另做2任务/3消息和1任务/1消息的提示词定向回归，三轮报告与指令分别保留。实际多轮已验证“模糊求助→最少追问→补充账号锁定信息→重新检索→15分钟”；最后缺报价回复使用自然语言，不再列内部检索版本或空引用字段。额外题为重复回归，不算新增独立题。正常Agent已刷新最新指令，检索规则仍是冻结的V4.1，首次16题分数不变。
